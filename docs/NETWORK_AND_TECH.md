# SUBSISTENCE — сеть, производительность, античит, HDRP

## 1. Архитектура сети

```
КЛИЕНТ                                   СЕРВЕР (30 Гц)
├── ввод (PlayerInput)                    ├── CommandValidator (rate / speed / distance)
├── предсказание: движение, отдача,       ├── DamageRouter → SurvivalSystem, строения
│   вспышка выстрела, звук                ├── Building (стройка, апгрейд, рейд-урон)
├── SnapshotInterpolator (20 Гц буфер)    ├── LootContainer (лут и респавн)
│                                          ├── MonsterRuntime (FSM, сенсоры)
└── InterestGrid 32×32 м — только         └── BroadcastSnapshots по AOI
    ближние сущности (LOD репликации)
```

**Транспорт абстрагирован** — `INetHost` (`Net/NetworkBridge.cs`). Реализации:
- `LocalHost` — офлайн/сингл (используется для тестов и редактора);
- `MirrorNetworkHost` — Mirror (`Net/MirrorAdapter/MirrorNetworkHost.cs`, активен при define `MIRROR`).

Геймплейный код обращается только к `NetworkBridge.IsServer` / `NetworkBridge.Command(...)`,
поэтому смена транспорта не переписывает логику (если позже захочешь Netcode/Photon — только новый адаптер).

### 1a. Что уже проходит через сеть

| Механика | Файл | Как идёт |
|---|---|---|
| Двери и замки (16_doors) | `Net/DeployNet.cs` + `Building/Doors.cs` | клиент шлёт `ClientCommand.UseDeployable` / `SetCode` (действие + позиция двери), сервер валидирует дистанцию ≤ 9 м, парный ключ (`ItemStack.metaTag`) или код замка, применяет состояние и рассылает RPC `door.state` / `door.lock` / `door.grant` / `door.deny` |
| Спавн деплоев (30–31) | `Net/SpawnNet.cs` | клиент шлёт `ClientCommand.PlaceDeployable` (предмет + точка + поворот), сервер проверяет дистанцию ≤ 7 м, привилегию TC и свободное место, создаёт объект и рассылает `object.spawn` (netId, itemId, pos, yaw, owner); удаление — `object.despawn`; новому игроку при подключении высылается весь мир |
| Стройка (30–31) | `Building/BuildSystem.cs` + `Net/SpawnNet.cs` | клиент шлёт `ClientCommand.PlaceBuilding` (элемент + тир + поворот + точка), сервер повторяет всю валидацию `BuildController` (дистанция, ресурсы через `CanAfford/Pay`, чужой TC, занятое место), создаёт блок через общий `BuildController.SpawnBlock` и рассылает `object.spawn` вида `block` (netId, piece, tier, rot, pos, owner, buildingId) |
| Инвентари и лут (30–31) | `Net/InventoryNet.cs` | клиент шлёт `ClientCommand.InvSync` (дельта слотов ~5 раз/с, редко — полная сверка), сервер держит **зеркало** рюкзака каждого игрока и по нему проверяет/списывает предметы; выдача обратно — адресно `inv.give` / `inv.take`. Контейнеры адресуются «хэндлом»: лут-ящики мира — по позиции, деплои (сундук, печь, мешок с трупом) — по **netId** (`SpawnNet.ById`), у печи вторая ёмкость — `sub=1`. `LootOpen` → `loot.contents` (все ёмкости объекта), `LootTake`/`LootStore` с проверкой дистанции ≤ 4.5 м и места в рюкзаке, изменения уходят `loot.slot` **только тем, у кого этот контейнер открыт** (`_open`-реестр) |
| Предметы на полу (30–31) | `Net/SpawnNet.cs` + `World/LootSpawner.cs` | дроп: `ClientCommand.LootDrop` (предмет + количество + точка), сервер проверяет дистанцию ≤ 3.5 м и наличие предмета в зеркале, создаёт объект и рассылает `object.spawn` вида `loose`. Подбор: `ClientCommand.LootPickup` (netId), сервер проверяет дистанцию ≤ 4.5 м и **место целиком** (`ServerHasRoomFor` — сухой прогон по копии рюкзака), отдаёт предмет через `inv.give` и удаляет объект (деспавн уедет сам). Предмет исчезает через 15 мин — как в Rust |
| Смерть и мешок с лутом (30–31) | `Net/InventoryNet.cs` + `Net/SpawnNet.cs` | `ClientCommand.PlayerDied` (только точка и поворот): мешок собирает **сервер из своего зеркала**, а не из присланного списка — иначе игрок мог бы «нафармить» мешок чужими предметами. Проверки: дистанция ≤ 8 м от серверной позиции игрока и не чаще раза в 10 с. Мешок (`object.spawn` вида `bag`, адрес — netId) лежит 15 мин, у мёртвого инвентарь обнуляется в зеркале и уходит `inv.clear` ему на клиент |
| Бой и урон по игрокам (30–31) | `Net/CombatNet.cs` | монстры/взрывы/огонь живут только на сервере (`if (!IsServer) return;`) — их урон идёт через `CombatNet.ServerDamage`, а удалённой жертве уезжает адресный RPC `dmg` (она сама применит урон, кровотечение и смерть). Попадание игрока по игроку — `ClientCommand.HitPlayer` (оружие + точка + зона, **без числа урона**): сервер проверяет наличие оружия в зеркале, дистанцию (дальность оружия + 2.5 м), близость точки попадания к цели, угол взгляда ≤ 65° и линию видимости, после чего сам считает урон по `WeaponTable` (с падением по дистанции и множителем зоны). Своё здоровье клиент сообщает `PlayerHealth` (2 раза/с): сервер принимает только ухудшение — «вылечиться» правкой пакета нельзя |
| Валидация частоты | `CommandValidator` | лимиты на команды (FireWeapon 0.033 с, PlaceBuilding 0.08 с…), 3 нарушения → кик |
| Админы/античит | `Net/AdminSystem.cs` | команды в чат-консоли, аудит-лог |

**Код замка по сети НЕ передаётся**: у клиента его просто нет, «НЕВЕРНЫЙ КОД» — ответ сервера.
Ключ — обычный предмет с `metaTag = keyId`; сервер сам ищет его в инвентаре игрока.

**Предсказание постановки есть (30–31).** Клиент ставит объект сразу и не ждёт сервера:

1. `SpawnNet.RequestPlace` / `PlaceBuilding` — запрос серверу;
2. `SpawnNet.PredictDeployable` (деплой) или `PredictBlock` (визуальная заглушка блока) — объект
   появляется в тот же кадр, предмет/ресурсы списываются оптимистично;
3. сервер присылает `object.spawn` — клиент **усыновляет** своё предсказание по предмету и позиции
   (`TakePending`) и присваивает ему netId, а не создаёт второй объект (модель не «мигает»);
4. сервер отказал — уходит `place.reject` (адресно), клиент убирает предсказание и **возвращает
   предмет/стоимость** (`Refund`); если сервер молчит дольше `PredictionTimeout` (2.5 с) — тот же откат.

Учёт прочности и стабильности остаётся серверным: предсказанный блок — только визуал, настоящий
блок создаёт сервер (поэтому у клиента нет своей «стабильности» и обвалов не расходится).

**Инвентарь — зеркалом, не «в лоб»:** клиент остаётся владельцем своих слотов (инвентарь живёт
в UI и в предсказании), но сервер держит его копию и распоряжается предметами сам: постройка,
постановка деплоя и навешивание замка списывают предмет **на сервере** (`InventoryNet.ServerPay`,
`ServerConsume`), а ключ от нового замка приезжает владельцу адресно `inv.give`. Поэтому
`SpawnNet.RequireServerInventory` теперь включён.

**Один игрок — один id:** в Mirror команды и RPC ходят по **netId игрового объекта**
(`MirrorNetworkHost.IdOf`), а не по `connectionId` транспорта — иначе «только тебе» не работало бы
(`PlayerRpc` → `IPlayerMessaging.SendToPlayer`). Офлайн такого разделения нет: `LocalHost` рассылает
сообщение, а адресат отсеивается на клиенте (`IsMine`).

**Содержимое ящиков считает только сервер** (`LootSpawner` заполняет контейнер при
`NetworkBridge.IsServer`): при открытии клиент получает серверное содержимое и перезаписывает
своё локальное — иначе у каждого игрока был бы «свой» лут. Респавн ящика тоже серверный:
после рефилла всем уходит `loot.contents`, и открытое окно обновляется само.

**Кто кому платит:** списание по инициативе игрока (постановка, стройка) делает сам клиент —
оптимистично и мгновенно, а сервер лишь повторяет это в зеркале (без `inv.take`: иначе предмет
списался бы дважды). Сервер уведомляет клиента (`inv.take`) только когда меняет его инвентарь сам:
например, при перекладывании предмета в ящик.

**Хранилища — серверные.** Сундуки (`StorageBox`) и печи (`Furnace`) открываются через
`InventoryUI.OpenDeployable(...)`: содержимое приходит от сервера, перекладывания идут запросами,
а печь после каждой плавки сама обновляет открытые окна (`InventoryNet.ServerContainersChanged`).
У печи в интерфейсе две сетки — вход и выход (`sub 0` / `sub 1`), как в Rust.

**Смерть — тоже серверная.** Умирающий клиент не создаёт мешок сам: он отправляет `PlayerDied`, а
сервер собирает мешок из зеркала, кладёт его в мир (`SpawnNet.ServerSpawnBag`) и обнуляет рюкзак
мёртвого — и в зеркале, и у него на клиенте (`inv.clear`), иначе после респавна остались бы копии.
Хост и офлайн делают то же самое локально (`PlayerEntity.DropLootBag`).

**Кто платит за предмет на полу.** Как и с постановкой: клиент списывает предмет у себя мгновенно,
сервер лишь повторяет это в зеркале (без `inv.take`). Подбор — наоборот: сервер проверяет
`ServerHasRoomFor` (берём целиком или никак) и выдаёт предмет адресно `inv.give`, только после
этого объект исчезает у всех.

**Кто считает урон.** Игрок → игрок: только сервер (клиент сообщает о выстреле, число урона не
присылает — подделать нельзя). Монстр/взрыв/огонь → игрок: сервер. Голод, радиация, кровотечение,
утопление: клиент (`SurvivalSystem` — это длинная симуляция), но с оглядкой на сервер: он принимает
только ухудшение и не даёт «вылечиться» пакетом. Смерть финализирует сервер: мешок собирается из
зеркала инвентаря (см. выше), здоровье в зеркале обнуляется (`CombatNet.OnPlayerDied`).

⏳ **Ещё не в сети (спринт 30–31):** предсказание лута (взятие из ящика ждёт ответа сервера ~RTT);
руда в залежах (`WorldDeposits.All` — добыча киркой/топором считается локально; сами залежи
раздаются генератором одинаково всем); **удары клиента по монстрам и постройкам** — их пока
применяет только сервер (`MonsterRuntime.ApplyDamage` и `BuildBlock` живут под `IsServer`), поэтому
для ремоут-клиента нужна серверная пересборка выстрела (`FireWeapon`/`MeleeAttack` — заглушки в
`MirrorPlayer.HandleCommand`); апкип/экономика и вайп-цикл.

## 2. Что делает 100+ игроков возможными

| Механизм | Реализация | Эффект |
|---|---|---|
| Server authority | урон/стройка/лут считаются только на сервере | нет «серверных» читов |
| AOI-сетка 32 м | `InterestGrid` + `BroadcastSnapshots` | трафик ∝ числу ближних объектов, не N² |
| Квантование | `BufferWriter.WritePosition` (float→ushort, шаг ~1.5 см на диапазоне −100…900 м) | позиция 6 байт вместо 12 |
| Единый формат позиции | везде `WritePosition(p, -100f, 1000f)` / `ReadPosition(-100f, 1000f)` | раньше часть сообщений писалась/читалась в диапазоне 0…500 м, и всё, что левее/ниже нуля, схлопывалось в 0 (деплои и блоки падали на плоскость x=0) |
| Снапшоты 20 Гц + интерполяция | `SnapshotInterpolator` (буфер 16, экстраполяция ≤150 мс) | плавно при 100 игроках на 12 Мбит/с |
| Лимит пакета | ≤64 сущности на снапшот (анти-MTU) | нет фрагментации UDP |
| Zero-GC буферы | `BufferWriter.Rent/Return` пул | нет GC-спайков в тике |
| Инкрементальные контейнеры | `ItemContainer.DirtyMask` (ulong) | ящик шлёт только изменённые слоты |
| Команды с частотными лимитами | `CommandValidator.MinInterval` | антиспам и анти-макро |
| Рейт-лимит движения | `ValidateMovement` (max speed ×1.35 + лаг-допуск) | анти-спидхак |

**Бюджет трафика на игрока (оценка):** 20 снапшотов × ~40 ближних объектов × ~14 байт ≈ **11 КБ/с** при полной загрузке
плюс команды (Move 30/с по 10 байт ≈ 300 Б/с). Итого **≈ 12 Мбит/с на 100 игроков** (без голосового чата).

## 3. Античит

1. **Частота команд** — таблица `MinInterval` (выстрел 33 мс, стройка 80 мс, лут 30 мс, крафт 100 мс).
2. **Движение** — `ValidateMovement`: предел `maxSpeed × dt × 1.35 + 0.5 м` (компенсация лага).
3. **Дистанция взаимодействия** — `Balance.MaxInteractDistance = 3 м` для лута, `6 м` для стройки (проверяется и на сервере).
4. **Привилегии** — нельзя строить/ломать чужое в радиусе TC (`BuildingPrivilege`).
5. **Серверный урон** — клиент присылает только направление; попадания считает сервер (`FireHitscan` внутри `NetworkBridge.IsServer`).
6. **Накопитель нарушений** — 3 нарушения → отключение соединения (`MirrorSubsistenceManager.OnServerCommand`).
7. **Валидация лут-операций** — сервер проверяет, что игрок физически рядом с контейнером (по `InteractionRegistry`, добавляется в спринте 6).

## 4. Производительность

- **Геометрия**: один меш на уровень (`MeshBuilder`, `indexFormat = UInt32`) + `MeshCollider` → ~6 draw call на 3 уровня.
- **Освещение**: точечные лампы генерируются как данные (`WorldEnvironment.Lights`) + эмиссивный материал; реальные `Light` — только в радиусе 30 м от игрока (`pixelLightCount = 4`).
- **Монстры**: FSM с сенсором раз в Update, но `Physics.OverlapSphere` кэширован (NonAlloc-буферы), A* по графу с лимитом итераций 4096.
- **Сервер**: тик 30 Гц, все «тяжёлые» системы (гниение, апкип, респавн лута, волны монстров) — на таймерах от 20 с до 10 мин.
- **GC**: инкрементальный GC включён (`PlayerSettings.gcIncremental`), сетевые буферы и списки — в пулах/переиспользуемые.

## 5. HDRP: что нужно сделать один раз в Unity

1. `Subsistence → 5. Создать HDRP Asset + назначить` (или вручную: Assets → Create → Rendering → HDRP Asset).
2. `Window → Rendering → HDRP Wizard` → **Fix All** (создаст Global Settings, настроит объёмный свет и тени).
3. Рекомендуемые настройки под нашу атмосферу:
   - **Volumetric Fog**: on, base density 0.35 (пыль/дым в бассейнах и станции);
   - **SSAO**: on, radius 0.6 (обои и ковёр получают объём);
   - **Shadows**: PCSS off (дорого), фильтр High, дистанция 60 м;
   - **Color Grading**: LUT с уклоном в жёлто-зелёный (L0), холодный циан (L1), серый + оранжевый акцент (L2);
   - **Motion Blur**: низкий; **Bloom**: 0.15 (лампы должны «светиться»);
   - **Refraction/SSR**: включать только на воде бассейнов (материал `poolWaterMat`), SSR = Screen Space.
4. Материалы создаются кодом (`RuntimeBootstrap.CreateMaterials`, шейдер `HDRP/Lit`, фоллбэк `Standard`), поэтому проект играбелен даже до импорта текстур.
