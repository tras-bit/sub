# SUBSISTENCE — сеть: следующий шаг после альфы (ответы 18в и 19б)

Ответы **18в** («дальше — сеть: тест на 2–4 игрока, Mirror») и **19б** («Mirror пока офлайн,
но архитектура готова») означают: сейчас игра запускается одиночной, а сетевой слой уже разложен
по полочкам и ждёт включения.

## Что уже есть (офлайн-ветка)

* Транспорт абстрагирован: `Net/NetworkBridge.cs` + реализации `LocalHost` (офлайн, по умолчанию)
  и `MirrorNetworkHost` (живёт под define `MIRROR`).
* Весь геймплей общается с миром **только** через `NetworkBridge.IsServer` / `Command(...)` —
  поэтому включение сети не переписывает логику.
* Сервер-авторитет уже написан для: двери/замки, деплои, стройка, инвентарь и лут, дроп предметов,
  смерть и мешок с лутом, урон по игрокам, валидатор частоты команд, админы/античит.
* Полная раскладка «механика → файл → как идёт по сети»: `docs/NETWORK_AND_TECH.md`.

## Включить Mirror (5 шагов)

1. Unity Hub → Packages → Add package by name → `com.mirror-networking.mirror` (v96).
2. Project Settings → Player → Scripting Define Symbols → добавить `MIRROR`.
3. Меню **Subsistence → Сеть → собрать Mirror-сцену** (создаёт хоста, спавнер игроков,
   привязывает `MirrorNetworkHost`).
4. Хост: Play → «Сеть → Хост». Клиенты: «Сеть → Подключиться», адрес хоста в меню.
5. Проверить: два клиента видят друг друга, чужие постройки/деплои/двери синхронны.

## Что проверяем на тесте 2–4 игроков (приёмка ответа 18в)

| Проверка | Ожидание |
|---|---|
| Движение и стрельба | расхождение позиций < 30 см, попадания считает сервер |
| Стройка | оба игрока видят блоки; чужой TC блокирует стройку в радиусе |
| Инвентарь и лут | ящик открыт у двух игроков — изменения видны обоим, нет «дублирования» предметов |
| Двери и замки | код замка клиенту не уходит; чужая дверь не открывается |
| Смерть | мешок собирает сервер из своего зеркала; у мёртвого рюкзак пуст у всех |
| Валидатор | телепорт/спидхак → 3 нарушения → кик (лог `AdminSystem`) |
| Просадка | 4 игрока в одном зале: снапшоты 20 Гц, AOI 120 м, тик сервера 30 Гц |

## Если позже захочешь другой транспорт

Ничего в игровом коде менять не нужно: пишется новый адаптер `INetHost` (Netcode/Photon/свой),
`MirrorNetworkHost` остаётся как эталон. Приёмка та же таблица.

## Онлайн 100+ (расширение приёмки 18в → требование «сеть 100+ человек»)

### Что уже в коде (alpha 1.0.0)

| Механизм | Где | Значение |
|---|---|---|
| Слоты / мягкий лимит | `Core/IDs.cs` (`Balance`), `MirrorNetworkHost.OnServerConnect` | 128 слотов; новым отказ выше 112 онлайн (цель — 100+) |
| Interest management (AOI) | `MirrorNetworkHost.BroadcastSnapshots` + `InterestGrid` | 120 м до 64 игроков, плавно до 55 м на 128 |
| LOD снапшотов | `MirrorNetworkHost.LoadProfile` | 20 Гц → 16 Гц (период ×1.25) при онлайне > 64 |
| Лимит сущностей в пакете | там же | 64 → 24 (анти-MTU, ~0.9 КБ на пакет) |
| Ноль мусора в рассылке | `NetworkBridge.BufferWriter.Reset()` | один буфер на всю рассылку вместо Rent/Return на соединение |
| Метрики | `MirrorNetworkHost.PrintLoad()` раз в 10 с | онлайн, AOI, Гц, пакеты/с, КБ/с исходящего и на игрока, сущностей в пакете, размер реестра |
| Приём снапшотов на клиенте | `Net/SnapshotClient.cs` | разбор `[время][count]+N×[netId][данные]`, `NetEntity.Find` → `ReadSnapshot` (интерполяция), счётчики сущностей/с и КБ/с |
| Пороги приёмки в коде | `Core/IDs.cs` (`NetKbPerPlayerCap`, `NetMbpsTotalCap`, `NetTickBudgetMs`) | стенд печатает ОК/ПЕРЕБОР по каждому |
| Команда проверки | консоль меню → `NETSTAT` | что реально идёт по сети: приём, трафик, реестр сущностей |
| Тик сервера | `Balance.TickRate` | 30 Гц (команды); снапшоты — отдельным таймером |

### Оценка трафика (AOI 120 м, средний зал)

* снапшот: 8 Б заголовок + ~14 Б на сущность (netId 4 + позиция 6 + поворот/состояние ~4);
* 25–45 сущностей в кадре → 350–650 Б на игрока;
* 20 Гц → **7–13 КБ/с на игрока вниз** (≈ 0.06–0.1 Мбит/с);
* 112 онлайн → **0.8–1.5 МБ/с исходящего** (≈ 7–12 Мбит/с), входящего ~0.4 МБ/с;
* команды вверх: 30 Гц × ~12 Б ≈ 0.4 КБ/с на игрока.

### Железо сервера (headless-билд)

| Онлайн | CPU | RAM | Канал |
|---|---|---|---|
| 25 | 2 vCPU | 4 ГБ | 10 Мбит/с |
| 64 | 4 vCPU | 6 ГБ | 20 Мбит/с |
| 112 | 6–8 vCPU | 8–12 ГБ | 30 Мбит/с |

### Стенд нагрузки (уже в коде)

| Что | Как запустить |
|---|---|
| Headless-сервер | `Subsistence.exe -batchmode -nographics --server --port 7777` |
| Клиент | `Subsistence.exe --client --host <ip> --port 7777` |
| Серверные боты (112) | `Subsistence.exe -batchmode -nographics --load-bots 112` |
| В редакторе | консоль меню → `LOADBOTS 112` (или `BOTS 64`) |

Что делает стенд `Net/NetLoadTest.cs` + `Net/CmdLine.cs`:

* поднимает N ботов-прокси (`LoadBot : NetEntity`) — те же AOI-запросы и `WriteSnapshot`,
  что у настоящих игроков, боты бегут по кругу со скоростью 4.2 м/с, «дыша AOI» как в бою;
* каждые 1/20 с делает **холостой прогон рассылки**: AOI-запрос + сборка пакета для каждого бота,
  сокеты не трогаются — мерим именно серверную цену;
* печатает в консоль раз в 10 с: `[netload] ботов 112, AOI 55 м, 16 Гц, лимит пакета 24 |
  в среднем в кадре 18.4 сущностей, снапшот 545 Б | трафик 8.5 КБ/с на игрока,
  суммарно 0.93 МБ/с (7.4 Мбит/с) | прогон 0.42 мс, худший AOI 0.031 мс`.

Что изменилось после первого прохода по сети (alpha 1.0.0):

* у снапшота появился **потребитель** (`Net/SnapshotClient.cs`): раньше пакет собирался и уходил,
  но клиент его не читал, а поле `count` уходило нулём — теперь счётчик заполняется
  (`BufferWriter.WriteUShortAt`), а клиент ищет сущность в реестре `NetEntity` и отдаёт данные
  в `ReadSnapshot` (интерполятор). Пакет байт-в-байт повторяет боевой и в стенде;
* реестр `NetEntity` по netId (`Find`, `RegisteredCount`) — без него приём пакета невозможен;
* у клиента есть счётчики приёма (сущностей/с, пакетов/с, КБ/с, неизвестные netId) — их печатает
  сервер раз в 10 с и команда `NETSTAT`; стенд печатает их вместе с вердиктом приёмки;
* статическая проверка `tools/check_net_scale.py` (N1–N9) следит, чтобы формат снапшота и его
  приёмник не разъехались снова: она падает, если `count` не заполняется или приёмник пропал.

Чего ещё нет (и не выдаём за готовое):

1. **Бот-клиенты по сети** — стенд мерит серверную часть; чтобы проверить интерполяцию,
   потери пакетов и «чувство» боя, нужны клиенты-боты с тем же `--client` (пишется поверх
   готового адаптера, отдельная задача). Разбор снапшотов на клиенте теперь есть — боту
   останется только «нажимать кнопки» и мерить расхождение позиций.
2. **Прогон на реальном железе** — цифры выше появятся после первого запуска стенда;
   их надо сверить с таблицей приёмки и, если сервер не держит, уменьшить `softPlayerLimit`
   или AOI-профиль (`MirrorNetworkHost.LoadProfile`). Никаких «100+ уже проверено» до прогона.

### Приёмка 100+

| Проверка | Норма |
|---|---|
| Частота снапшотов при 112 онлайн | ≥ 15 Гц (профиль даёт 16) |
| Тик сервера | ≥ 28 Гц; если ниже — уменьшить `softPlayerLimit` |
| Исходящий трафик | ≤ 12 Мбит/с при 112 онлайн |
| Ошибка позиции чужого игрока | ≤ 0.5 м (квант 0.01 м + интерполяция) |
| Постройка при 100 онлайн | блок виден всем в AOI за ≤ 2 снапшота |
| Урон и смерть | считает сервер, «двойных» смертей нет |
| Реконнект | слот освобождается, повторный вход ≤ 5 с |
| Память сервера | ≤ 12 ГБ RSS, рост за 6 часов ≤ 15 % |
| Античит | 0 ложных киков на 100 ботов; спидхак — кик на 3-м нарушении |

**Порядок:** тест 2–4 игрока — сразу после первого открытия проекта в Unity (5 шагов выше);
тест 100+ — после headless-билда и ботов (пункты 1–2), то есть следующий шаг после обкатки на 10–20 игроках.
